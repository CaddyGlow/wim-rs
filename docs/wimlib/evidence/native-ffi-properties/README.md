# Native C image properties: partial implementation

The unchanged original `wimlib.h` client links against original 1.14.5 and the Rust cdylib. Nine symbols are implemented: `wimlib_get_image_name`, `wimlib_get_image_description`, `wimlib_get_image_property`, `wimlib_set_image_name`, `wimlib_set_image_descripton` (the upstream misspelling), `wimlib_set_image_flags`, `wimlib_set_image_property`, `wimlib_image_name_in_use`, and `wimlib_resolve_image`.

`contract-red.log` records the client initially failing to link against the native library because the symbols were absent. `differential.json` records identical 1,498-line output for an original-library-created two-image WIM. Cases cover missing/invalid images, exact name matching and collisions, signed/whitespace/overflow selectors, Unicode property text, NULL/empty deletion, slash and indexed XML paths, validation precedence, and retained getter pointers after a failed mutation. A complete nonzero-byte sweep checks setter/getter/name resolution/name-in-use behavior for bytes 1–255, including rejected controls and accepted arbitrary high bytes. A second sweep creates, retrieves, and removes paths beginning with each byte 128–255. Three Rust ABI tests additionally check cached-pointer stability across cache insertions and exact Unicode name resolution. Getter buffers are owned by the handle and retained until `wimlib_free`; callers must access the handle exclusively while getters populate its cache. Mutation does not promise old property text remains semantically current.

Linux properties additionally support arbitrary bytes through the actual owned XML tree: element names, attribute names/values, and text are byte vectors, rather than a getter-only overlay. `get_property_bytes`, `set_property_bytes`, `name_bytes`, `name_in_use_bytes`, and `resolve_image_bytes` expose this representation to the ABI. Safe `str` accessors validate UTF-8; `to_xml_bytes` serializes the tree losslessly with upstream entity escaping. Both `to_xml` and `encode_utf16le` return `Result`. The String API requires valid Unicode UTF-8, while UTF-16 serialization accepts upstream WTF-8 surrogate codepoints and returns error 31 only for malformed byte sequences. Every native archive writer propagates serialization failures. Existing format clients were migrated to the fallible serialization API.

The additional 55-line raw-platform-text differential is exact in both libraries. It sets name byte `ff`, retrieves it unchanged, resolves it, detects a collision, and obtains error 31 when writing it. It also creates a non-UTF-8 element path with non-UTF-8 text; writing fails with 31 even after deleting its text-bearing child because the invalid ancestor remains in the tree. Deleting that ancestor restores successful writing. The final output WIMs pass original-library verification. Eight additional cases set/get/write/reopen high and low unpaired surrogates, a separately encoded surrogate pair, the corresponding supplementary codepoint, and U+FFFE/U+FFFF. Reopening normalizes separately encoded surrogate pairs exactly as upstream. `raw-text-write-red.json` records the initially failing write stage (native writer rejected the original ALL_IMAGES selector with error 18); the writer was corrected to the original constant -1. Five format regression tests exercise raw byte/Unicode distinction, ancestor retention, selection/append cloning, serialization recovery, surrogate element names/text and pair normalization. Three conversion tests round-trip every one of the 65,536 individual UTF-16 code units, verify pair/surrogate encoding and reject malformed UTF-8 without replacement; the exhaustive single-unit sweep is native regression coverage, while the C client supplies independent boundary-case evidence. `platform-text-tests.log` records the conversion/XML tests.

Reproduce from the repository root:

```sh
cargo build --manifest-path Cargo.toml --target-dir target --locked -p wim
python3 scripts/wimlib/check-properties-abi.py --native target/debug
cargo test --manifest-path Cargo.toml --target-dir target --locked -p wim-format -p wim --all-features
```

These exports remain **partial**, not host-verified full drop-in symbols. Windows wide-string behavior is untested. The property adapters now preserve unpaired UTF-16 through shared WTF-8 conversion helpers, but this has not been validated against a Windows-built original library. Global initialization/locale behavior and allocator-hook/failure-injection semantics are not implemented; XML and string-cache allocation can still abort on memory exhaustion. The corresponding C write implementation has separate incomplete flags, progress, and buffering gates. Empty-image ownership and its API evidence are documented separately under `native-ffi-handles`.
