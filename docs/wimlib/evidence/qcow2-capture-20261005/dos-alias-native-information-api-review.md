# Native short-name API review (2026-10-06)

The three actual scratch ordering rounds select the requested directory entry: whichever same-directory or cross-directory hardlink is opened first receives its requested alias. Assigning either remaining link fails with Win32 error 183. All links are cleared before each round and independent parent enumeration confirms no prior aliases. This demonstrates working per-link selection, but does not demonstrate simultaneous aliases on all hardlinks. The hash-bound observations are in `v12-dos-alias-hardlink-ordering-result.json`; all three links also change their file change-time, so this is not full metadata invariance.

[FILE_INFO_BY_HANDLE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ne-minwinbase-file_info_by_handle_class) contains no short-name setter class. [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) therefore provides no documented `FileShortNameInfo` route. Passing Native API class number 40 to this different enum would not establish supported behavior.

[NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile) documents Native API class `FileShortNameInformation` (40), an NTFS handle with DELETE access, and a FILE_NAME_INFORMATION buffer. Its documentation includes user-mode naming guidance, but the requirements identify the driver DDI/kernel library. It does not promise a bypass of filesystem short-name restrictions.

[MS-FSA FileShortNameInformation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/13f8d991-c37a-4156-8e29-9200c13441c9) defines selection through Open.Link and rejects assignment when another link of the same file has a nonempty short name, regardless of parent directory. Separate sibling name conflicts are another rejection condition. This matches the observed first-link success and subsequent collisions. The specification also describes change-time updates. This is documented protocol semantics consistent with the experiment, not a traced proof of the internal implementation of SetFileShortNameW.

No different supported setter that restores multiple simultaneous hardlink aliases was identified. A direct NtSetInformationFile experiment would compare API entry points, not test a documented alternative capability; there is no evidence here to justify expecting it to bypass the same restriction. Do not change source or installed aliases, reduce the 101769-alias requirement, or credit this scratch result as restoration. A future candidate must address exact per-directory-entry metadata during deployment or creation and prove full mappings and metadata independently, including actual multiple-alias hardlinks where required.
