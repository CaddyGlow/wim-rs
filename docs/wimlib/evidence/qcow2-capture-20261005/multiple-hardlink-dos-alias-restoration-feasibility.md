# Multiple hardlink DOS alias restoration feasibility

Actual current source needs 378 file-reference groups with two to four DOS-bearing links (979 links). Setter, automatic creation, and rename experiments do not restore this requirement. All 101769 source mappings remain mandatory.

The vendored Rust NTFS crate provides readers: `Ntfs::new` and record/index traversal take Read+Seek, FILE_NAME is decoded with BinRead, and there is no Write/BinWrite filesystem writer implementation in vendor/ntfs/src. Its existing readers can independently validate a future writer; they cannot currently update FILE_NAME attributes or directory B-trees.

[Microsoft FileShortNameInformation semantics](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/13f8d991-c37a-4156-8e29-9200c13441c9) select the opened link but reject setting when another link of the same file already has a short name. [Microsoft hardlink backup guidance](https://learn.microsoft.com/en-us/windows/win32/backup/backing-up-and-restoring-hard-links) recreates links with CreateHardLink. [WIN32_STREAM_ID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-win32_stream_id) defines BACKUP_LINK, but does not document replay of arbitrary raw FILE_NAME records or multiple DOS namespaces. No supported per-link backup/native API bypass was established here.

[NTFS-3G's own extended-attribute documentation](https://github.com/tuxera/ntfs-3g/wiki/Using-Extended-Attributes) explicitly discontinues DOS-name xattr operations on files with multiple names because of corruption bugs. Thus system.ntfs_dos_name is not a supported solution for these groups. This is an API limitation, not evidence that the observed on-disk source aliases are invalid.

A concrete Rust option is a new offline NTFS metadata transaction writer, operating only on a stopped, exclusive disposable target clone. It must bind each desired link by volume serial, full file reference with sequence, parent full reference, and raw long-name UTF16; enumerate every existing namespace entry and detect collisions under the actual volume $UpCase collation. It must update both the inode FILE_NAME attributes and matching parent $I30 index keys, including namespace flags and associated file references; editing only one representation is insufficient. Variable-length names require index ordering, splitting/rebalancing, index allocation and bitmap growth, resident attribute space management, attribute-list/extents, runlist allocation and $Bitmap/MFT consistency. Multi-sector update-sequence fixups must be regenerated on every affected FILE/INDX record. Preserve security, all timestamps and stream extents explicitly; do not copy source parent references into a different target volume.

The first prototype can handle a deliberately bounded scratch case with sufficient existing record/index slack and abort atomically on every unsupported geometry. It must plan all bytes before mutation, retain the original clone plus hash-bound before/after sector maps, apply to a separate candidate, and expose no production path until meaningful failure/crash tests pass. Such a prototype is not full 378-group support; full support needs growth and redistribution cases before any release claim.

Validation must independently read every MFT namespace and parent index reference, verify all required long/short paths refer to the same full target ID, and compare full stream hashes/raw SD/EA/ObjectID/timestamps/link counts before and after. Then boot the disposable candidate with normal Windows, repeat no-follow mappings, run filesystem consistency checks, reboot, and repeat all 101769 source aliases. The exact observed multi-alias source groups must remain a separate mandatory challenge. This is a substantial new writer capability; no mutation or production change was made in this review.
